## 1. 固定输入和对照方法

基线固定为2026.11.04.1归档及其SHA；候选版本逐个记录归档/源码SHA。manifest记录原视频/SRT、模型PT/OM、检测结果、配置、遥测offset、源时间/帧号、adaptive决策、运行库、驱动、NPU、CPU/cgroup及输出设置。凭据只记录配置项是否存在，不写明文或可还原值。

两层对照：

1. **确定性P2回放**：相同检测输出、图像运动所需帧/已验证变换、遥测、源帧和时间输入，直接经过真实跟踪/在线节点及真实输出边界。只用手工填Track对象不能证明关联/业务一致。输出每帧业务记录作为基准。
2. **端到端原生运行**：同视频/SRT、OM模型、参数和完整四进程入口；检测器若有数值差异，单独登记，不能归咎跟踪改动。业务等价以固定检测回放为准，现场吞吐以真实端到端为准，两者都须通过。

拟新增驱动：`scripts/benchmark_tracker_replay.py`、`scripts/compare_pipeline_business_outputs.py`、`scripts/benchmark_pipeline_transport.py`。其中benchmark_pipeline_transport.py已实现并可执行；另增加门控专项benchmark_association_gate.py，其余两个完整回放/差分驱动仍是拟定接口，不能作为已可执行命令引用。回放应有固定seed、隔离输出、非零失败退出码、差分文件与显式原版/候选参数。

稳定业务ID、帧/源时间、事件时间不能从差分中排除。可规范化新建的运行UUID/运输元数据、封存墙钟及真实性能叠字，但必须逐字段白名单；固定同一Mission时基用于摘要对照，不删除整段identity或timestamp来“消差”。基准运行和候选写入各自隔离数据库/Topic空间，防止幂等身份冲突污染对照。

## 5. 故障矩阵

| ID | 注入点 | 预期 |
| --- | --- | --- |
| F01 | P1/P2/P3/P4任一worker异常或SIGKILL | 整管道失败，父等待/核对最终状态，标记incomplete，清理所属进程/nonce共享内存 |
| F02 | 归档队列持续满、ACK无进展10秒 | 明确失败，保存已持久包及可收尾发送端未确认包，无静默丢轨迹 |
| F03 | 慢但持续前进ACK、空队列长模型预热 | 不误判停滞；不能按最老包绝对年龄错误中止 |
| F04 | journal fsync/ENOSPC、发送端保存也失败 | 失败原因明确，不报成功；保留已有持久数据，保存失败不能伪称数据已保存 |
| F05 | 同序号同内容、重复/缺失/冲突增量、错误角色 | 幂等重复可接收，缺口/冲突拒绝；点数/水位核对不绕过 |
| F06 | 图像EOF缺失、乱序证据、文件丢失/hash错误 | 不提前发布证据或封存成功；双EOF与待配对集合核对 |
| F07 | Kafka断线、延迟恢复、关键发送排空超120秒 | 关键spool保留并报告失败；普通实时策略保持；不自动回补消费跳过区间 |
| F08 | 最后一个worker退出瞬间失败、停止信号 | 不因显示已结束或所有worker已退就宣布成功；无僵尸/泄漏 |
| F09 | 新版数据后退回旧消费者、旧包root日志权限、重复启动 | v2降级门禁、root权限检查、单实例和兼容版本失败恢复保持 |

SIGKILL不能执行被杀进程的内存落盘；保证已ACK数据持久、其余状态不伪称完成。发送端可处理退出时保留未确认包；因磁盘故障无法保存时记录事实，不承诺物理上不可能的“任何故障零损失”。

## 6. 性能试验设计

### 微基准与完整回放

- 运行库/硬件相同，热身20次、测量至少100次，内存重负载可用固定连续帧回放替代大量重复分配，并记录理由。基线/候选交替至少3组，报告中位数/P95/最大值、当前线程/进程CPU、RSS/PSS及峰值、序列化字节。
- 每帧P2总服务时间与各互斥子阶段同时计时；队列等待、编码和推理分列。以CPU采样验证热点，不能用logger名代替函数归因。
- 对固定250目标、500与5000历史的相同尾迹分别测量；制作长回放确认没有历史增长回归。目标数量、成熟程度、冲突候选数、轨迹长度分桶展示，不能用低目标数的候选版本对比高目标数原版。
- 性能门槛未达但业务正确，也不能标记“FPS已修复”；混合结果或统计噪声只列观察，不扩测到出现一次好成绩就停止。

### 现场端到端A/B

1. 先记录原生产配置/版本与资源哈希；按维护窗口停止任务，保存现场数据。不得同时跑基线/候选重负载任务。
2. 从同一原视频起点/相同任务配置运行。建议预热至少60秒，并进入成熟目标负载；每次选择同一源时间/帧区间作为有效窗口。若慢处理下原素材剩余不足，另选有足够长度的同源视频，不拼接无关窗口。
3. 预热后每版至少连续300秒有效墙钟数据；正式对照优先选取同一连续源帧区间，长度须确保两版各自完成该区间都需要至少300秒有效墙钟，分别按该区间完成帧数/实际耗时计算吞吐。若只能采固定300秒，则两版看到的源帧范围不同，只作监测，不能直接充当最终同负载收益；必须另补相同源帧区间及负载分桶对照。先做一组灰度，正式接受收益至少3组交替运行，记录温度、其他任务、I/O与NPU负载差异。
4. 每30秒记录P2已处理、P3已渲染、P4已合流及发送确认水位。端到端FPS=有效窗口完成帧差/单调墙钟差；启动/停止/封存阶段单列。源视频FPS、stride与网页刷新率另列，不乘stride充当处理FPS。
5. 以相同输入P2各帧服务时间对照定位收益，再看端到端完成吞吐；记录显示端/P4队列与ACK趋势，防止把瓶颈推到下游或暂存在队列。
6. 自然EOF检查关键排空、文件/摘要、Kafka身份、Platform事务落库和封存状态；任务结束后按ID/点数/事件/摘要逐项对账，不只看一次/ready或网页瞬时FPS。

建议的工程接受门槛（P0确认负载/噪声后锁定，不是现场收益承诺）：

| 项目 | P1目标 | P2累计目标 |
| --- | --- | --- |
| 现场平均完成吞吐 | 争取1.7–2.0 FPS，同负载至少提升15% | 争取2–3 FPS，同负载至少提升35% |
| P2帧服务P95 | 同输入不劣化超过10% | 同输入不劣化超过10% |
| 数据交接阶段 | 中位40–80ms，分项证明收益 | 不回归至原约189ms |
| 长历史/相同负载分桶 | 保留性能优势，无历史线性膨胀 | 保留性能优势，无历史线性膨胀 |
| 业务/可靠性/落库 | 所有必须断言通过 | 所有必须断言通过 |

吞吐改善率按同负载重复A/B汇总，存在明显噪声或运行间方向相反时不判定达标；绝对FPS与相对目标都记录，不能只选择好看的指标。RSS/PSS至少绘出时间趋势；生产预算须在P0锁定，不能事后加大内存/队列使测试通过。
