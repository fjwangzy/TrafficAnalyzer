## 1. 分册目标与边界

### 1.1 目标

建立覆盖算法质量、工程性能、数据质量、接口可靠性、业务可用性、安全合规和上线运营的统一体系，使每项交付都能回答：测什么、用什么数据测、如何计算、谁确认、达到什么条件算通过、失败后如何处置。

### 1.2 非目标

- 不在本分册重新定义 S1-S6 的业务规则和算法实现。
- 不把一次演示、单段视频效果或单一 Precision 作为合同验收结论。
- 不把现有 `inter_xqh` 单路口技术回归结果扩展解释为四类 AI 模型的业务验收。
- 不负责智慧交通主平台的派警、处置、归档和整体 SLA；只验证双方约定的 AI 事件联动边界。
- 不新增货车细分类验收项；S4 仅验收现有模型货车/非货车二分类及其适用边界。

## 3. 质量原则与判定层级

### 3.1 质量原则

1. **可复现**：每次评估固化代码、模型、配置、数据、标注和计算脚本版本。
2. **分层统计**：总指标必须下钻至类别、事件、路口、昼夜、天气、飞行高度、视角、遮挡、目标密度和质量状态。
3. **成对约束**：Precision 必须与 Recall、单位小时误报和有效覆盖率共同判断，禁止通过少报事件单独提高 Precision。
4. **质量可见**：无法可靠判断时输出降级、跳过或 `unmapped`，不得伪造权威 ID 或无依据结论。
5. **业务闭环分界**：AI 只验收到事件可靠投递和复核反馈回流；派警处置闭环由大项目验收。
6. **变更受控**：合同偏差、阈值、验收集和计算口径变更必须留书面记录，不得在验收后追溯调整以获得通过。

### 3.2 判定层级

| 层级 | 判定对象 | 结论 |
| --- | --- | --- |
| 用例级 | 单条功能、异常或接口用例 | 通过/失败/阻塞/不适用 |
| 指标级 | 某指标在总体及强制分层上的结果 | 达标/不达标/样本不足 |
| 分册级 | S1-S6 单个分册 | 通过/有条件通过/不通过 |
| 项目级 | 合同条款、四模型、集成和文档交付 | 通过/有条件通过/不通过 |

“有条件通过”只能用于不影响核心功能、安全、证据完整性和合同范围的遗留项，必须同时记录整改负责人、截止时间和复验方式。`【验收阻断】` 未关闭时不得判定分册或项目通过。

## 6. 验收数据集与标注治理

### 6.1 数据集分层

| 数据层 | 用途 | 可否用于调参 | 管理要求 |
| --- | --- | --- | --- |
| 开发集 | 模型训练、规则开发和错误分析 | 可以 | 记录来源、授权、清洗和版本 |
| 验证集 | 版本选择、阈值候选和回归 | 可以，但须记录 | 与开发集目标/时间/视频去重 |
| 预验收集 | 验证测试流程和计算脚本 | 原则上不用于最终调参 | 由测试负责人管理 |
| 正式验收集 | 合同验收 | 不可以 | 验收前冻结、记录哈希、权限隔离 |
| 运营抽检集 | 上线漂移与持续质量 | 仅用于后续批准版本 | 按周期抽样并保留复核结论 |

### 6.2 场景覆盖矩阵

正式验收方案至少明确以下维度及其组合；无业务适用性的组合须写明排除理由：

- 路口/路段类型、车道数量、交通组织和信号状态；
- 白天、夜间、晨昏及不同照明；
- 晴天、阴天，以及合同确认的其他天气范围；
- 悬停/巡飞、飞行高度、俯视/斜视和云台变化；
- 轻度/重度遮挡、低/中/高目标密度；
- 机动车、非机动车、行人及现有货车/非货车类别；
- 视频、遥测、RTK、路网和主平台链路的正常及降级状态。

【待补充：目标路口清单、维度枚举、各分层最小样本量与不可验场景】

### 6.3 标注规范

| 标注对象 | 必须定义的内容 | 质量控制 |
| --- | --- | --- |
| 目标与类别 | 可见性、类别边界、忽略区域、遮挡/截断 | 双人抽检、分歧仲裁 |
| 轨迹 | ID 连续、进入/离开、丢失、路网位置 | 轨迹级复核 |
| 换道/冲突 | 目标对、起止时间、冲突点、事件类型、不可判 | 交安专家仲裁 |
| 测绘 | 控制点、标准真值、量算对象、基准设备精度 | 测绘人员签字 |
| 执法线索 | 事实、围栏/规则版本、例外、证据可见性 | 执法/法制复核 |
| 主平台反馈 | 接收、拒绝、复核原因和统一事件映射 | 双方日志对账 |

数据去重必须至少覆盖同一原视频切片、连续帧、同一目标轨迹和同一事件，防止训练/验证/验收泄漏。标注修订后必须生成新版本并保留差异与仲裁记录。

### 7.3 运营目标与验收指标的区别

总 PRD 中“事故处理耗时、日均巡检次数、采纳率、自动取证率”等属于上线后的业务成功目标。除非合同明确约定，不能以试点期尚未积累到运营目标为由否定已通过的功能验收，也不能以运营采纳率替代算法和系统验收。

### 9.2 强制故障场景

| 编号 | 故障场景 | 预期行为 |
| --- | --- | --- |
| S7-FT-001 | 遥测中断/超时 | 坐标相关能力按规则降级或暂停，明确质量状态并告警 |
| S7-FT-002 | RTK/标定质量退化 | 不输出超出适用范围的确定性坐标/量算结论 |
| S7-FT-003 | 路网源断连 | 使用已校验缓存并标记 `stale`；无缓存标记 `missing` |
| S7-FT-004 | 路网版本不一致 | 标记 `version_mismatch`，不得混用或回写历史事件 |
| S7-FT-005 | Kafka/主平台断连 | 持久化重试、恢复补发，超过策略进入死信并告警 |
| S7-FT-006 | 回执超时/乱序/重复 | 以幂等键和状态规则收敛，不生成重复业务事件 |
| S7-FT-007 | 证据存储不足/调阅失败 | 告警并阻止不完整证据进入“证据完整/可交付”状态；案件归档由主平台负责 |
| S7-FT-008 | 管道进程崩溃 | 按批准策略重启，连续失败进入错误状态并通知运维 |
| S7-FT-009 | 模型版本异常 | 按路口/模型停止或回滚，不污染未灰度范围 |
| S7-FT-010 | PostgreSQL/TimescaleDB 短时不可用 | 持久化缓冲并告警，恢复后按原幂等键补写；不得静默丢失或写回旧真源 |
| S7-FT-011 | 双写结果不一致 | 阻断切读/退役，保留差异样本并按批准规则补偿，不自动选择更有利结果 |
| S7-FT-012 | TimescaleDB chunk/保留/压缩策略异常 | 停止危险策略，保护未归档数据并回滚配置，记录影响范围 |
| S7-FT-013 | `road9` 备份恢复或故障切换 | 在批准 RPO/RTO 内恢复，普通表与 Hypertable 的事件、指标和幂等状态一致 |
| S7-FT-014 | Producer 队列满/Kafka 发送失败 | 轨迹、冲突、AI事件和证据引用进入持久化补发且不静默丢失；允许丢弃的指标产生缺口和丢弃计数 |
| S7-FT-015 | Consumer 在 inbox/事实/offset 各提交点崩溃 | 恢复重放后最终只有一个事实结果；数据库失败前不得提交 offset，同 ID 不同 hash 隔离告警 |
| S7-FT-016 | 新旧统计链路同时写入 | 对账识别 Telegraf/Platform 重叠，不把同一窗口重复计入迁移结果 |

## 12. 发布、灰度与回滚

### 12.1 发布包

每个候选版本至少包含：代码/镜像标识、模型及哈希、配置模板、规则版本、路网适配版本、schema 版本、数据库变更说明、测试报告、已知限制、升级/回滚步骤和负责人。

### 12.2 灰度策略

- 灰度单位至少支持路口和模型；S4 规则变更还需支持按围栏/规则版本灰度。
- 新旧版本结果不得在同一事件中无标记混用，灰度期间必须保留版本维度指标。
- 模型、规则、接口和路网版本分别可追踪，禁止用单一“系统版本”掩盖局部变更。

### 12.3 回滚触发

立即停止或回滚的候选条件包括：证据完整性/越权问题、事件静默丢失、大规模重复事件、错误权威 ID、关键指标连续低于冻结门槛、资源耗尽影响主链路。具体阈值、观察窗口、批准人和恢复条件 `【待补充】`。
